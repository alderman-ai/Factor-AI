```
The lesson: prose-first building surfaces no engineering decisions, because
documents have no failure modes. Executability — not thematic constraint, not
discipline, not good intentions — is what generates learning.

Background. Factor-AI is a Factorio-themed harness being built in public, whose
explicit purpose is to push the operator (Alex) toward the deterministic side
of engineering: system architecture, traceable routing, loops, hooks, granular
subagent settings, clobber prevention across parallel working directories on one
machine. The first substantial pass at the world — call it V1 — was roughly 98%
authored by typing into Obsidian. The operator opened this session dissatisfied
with what came out and asked to pivot, describing what he wanted as "more
constraints, in the terminal, with quick feedback, to discover gaps in my
knowledge early and often, and to try things at a primitive level before
building at higher abstraction."

The diagnosis. V1 had machines and items but no actor. The operator surfaced
this himself, half-joking: "how did we forget the first time, the guy" — the
Factorio engineer, the character you crash-land as. That omission turns out to
be the whole explanation rather than a missing feature. With no actor, there is
no subject for a command to be issued to, no inventory to be wrong, no position
to be in the wrong place. Every interaction therefore defaults to prose *about*
a system rather than an action *within* one. V1 also had no tick — nothing that
advanced on its own. A world with no actor and no tick cannot fail, and a system
that cannot fail never asks you a question. That is why V1 read as a wiki in
costume, and why it taught the operator almost nothing despite the hours in it.

The evidence for the lesson arrived within about ten minutes of switching to
designing a V2 sandbox that has to actually run — a ship, the guy inside it, a
"darkness" area with a despair miner, despair accumulating on the guy, and a
skill called "Go Outside" that unlocks at five despair. Four genuine
mechanism-level decisions surfaced unprompted, none of which had ever come up
across all of V1:

(1) Derive vs. tick. The operator asked for "a loop that every 30 seconds adds
a new despair." A loop is not needed: despair at any moment is
floor((now - start) / 30), stored as a start timestamp on the guy and computed
whenever anything reads it. Derived state needs no daemon, is deterministic,
and survives a restart — which a background bash loop does not. Don't tick what
you can derive. The honest counter-argument is that a derived value only changes
when something looks at it, so nothing can interrupt you unprompted; if the
world must announce itself while you sit idle, that genuinely does require a
background process. The open question left with the operator was whether despair
needs to announce itself or merely be correct when checked.

(2) Absence vs. denial, which corrected the operator's assumption. He asked
whether unlocking was possible at all, or whether the full file tree had to be
deployed and visible with a PreToolUse hook blocking interaction — and said he
would prefer it not be visible. Checked against current Claude Code docs, two
native mechanisms beat the hook approach. First, live change detection: Claude
Code watches skill directories and picks up an added, edited, or removed
SKILL.md within the current session without a restart, so an unlock can
materialise a skill that genuinely did not exist a moment earlier. The one
catch is that the `.claude/skills/` directory itself must exist when the session
starts or the watcher is not watching it — the same empty-parent-populated-later
pattern as the eleven `.gitkeep` commits already in this repo. Second, and more
interesting, nested `.claude/skills/` directories below the working directory
are not loaded at startup; they load the first time Claude reads or edits a file
inside that subdirectory, and until then they do not appear in autocomplete and
cannot be invoked by name. That is proximity-gated knowledge — fog of war —
shipped in the product for free, and it stays committed to the repo, which suits
building in public. The general principle: native absence is stronger than
enforced denial, because absent information cannot leak into context at all,
whereas denial only refuses an action against information that is already
present. Denial also has open reliability gaps (claude-code issues #37540, Read
bypassing PreToolUse hooks in the VSCode extension, and #37210,
permissionDecision deny ignored for Edit). A fence you want to lean on can be a
hook; a fence that has to hold should be absence.

(3) Where actor state lives — a question that only exists once there is an actor
whose despair, position, and inventory must be written somewhere.

(4) Who the fog is for. Under materialise-on-unlock there is nothing to see at
all. Under nested-skill fog of war the operator can see the folder name in the
file tree while the model cannot see its contents — he knows a door exists but
cannot open it. Those are different games, and the choice is a design call, not
a technical one. Factorio shows you the tech tree; it does not show you the map.

The operator's own summary on seeing all four was "these are all the fun
learning opportunities I missed." They were not missed through carelessness.
They were structurally unavailable, because none of them can arise from writing
a document. The generalisation worth carrying forward: when the goal is to learn
a deterministic skill, prioritise the smallest thing that can run and fail over
the larger thing that can only be described. A thing with state can tell you no,
and being told no in under a second is the entire feedback loop the operator
was asking for.
```
