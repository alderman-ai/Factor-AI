```
A store that looks empty is not the same as a store that has been searched,
and the difference is invisible in the output.

Context: this session built the Pumpjack, a script that extracts Claude Code
session transcripts out of Claude Code's own storage (~/.claude/projects/)
and into the repository, producing two artifacts per session — a verbatim
JSONL copy called "crude" and a readable markdown rendering. The design
principle was that crude is the source of truth and must be complete, because
the render is deliberately lossy and re-runnable against it.

The first failure: while rendering, the extractor found 100 assistant
"thinking" blocks whose text field was an empty string. It reported, in a
README and a commit message, that Claude Code strips thinking text and
reasoning is unrecoverable. That conclusion happened to be correct, but it
was not earned — the only evidence was that one field in one file was empty.
No other storage location had been examined. The operator pushed back with
"surely they exist somewhere and we just need a better script." That
challenge was the right instinct and it forced an actual investigation:
decoding the signature blob to confirm its payload is encrypted rather than
plaintext, and running a recursive search across the whole of ~/.claude for
any file containing a non-empty thinking value. That search returned nothing,
across project storage, sessions/, cache/, backups/, and history.jsonl. Same
conclusion, but now supported.

The second failure was found by that same investigation and is worse, because
nobody was pushing on it. Claude Code spills large tool results out of the
JSONL into a sibling directory, <session-id>/tool-results/toolu_*.txt, and
the JSONL does not reference the path — the files are keyed by tool_use id
and located by convention. The extractor had copied only the JSONL. Four
files, roughly 2,800 lines of real content, had already been committed to a
public repository under a README asserting the crude was byte-for-byte
complete. The verification that had been run — comparing each copied JSONL
against its source — passed cleanly, because it was checking the wrong
question. It confirmed that what was copied was copied faithfully. It could
not detect what was never copied at all.

The nastiest property is the threshold. Spilling only happens above some size,
so a naive extractor is correct until abruptly it is not. Of three sessions
extracted, two had spilled files and one had none — and the one with none was
the session eyeballed to confirm the output looked right. A sampling check
against the healthy case validates a broken tool.

The generalizable form: absence of evidence was treated as evidence of
absence, twice, in the same hour, by the same process. Both times the
mechanism was identical — a check was run, it passed, and "passed" was
reported as "complete" without asking what the check was structurally
incapable of seeing. An integrity check that compares A to A cannot discover
that B exists. This is not a bug in the comparison; it is a bug in believing
the comparison answered a question it never addressed.

What follows practically. Before claiming a data store has been fully
extracted, enumerate the store rather than the thing you already know how to
read — list the directory, not the file you came for. Before reporting a
field as absent, search every plausible location and say which ones were
searched, so the claim carries its own evidence and a reader can see its
limits. When a verification passes, state explicitly what it did not cover;
"byte-identical to source" and "contains everything" are different assertions
and the gap between them is exactly where this failed. And treat a pushback
like "surely it's somewhere" as a prompt to go look rather than a prompt to
restate — the operator's challenge was worth more than the original claim,
and it paid for itself by turning up a bug that nothing else in the session
would have caught.
```
