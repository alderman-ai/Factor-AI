Yes — but not because two checks are safer than one. Redundant identical checks would be near-pure cost. It adds value because **they can't check the same things**, and you've named the split correctly.

## The decisive reason

An outbox is a directory on disk. Your PreToolUse hook only fires on Claude's writes, in a session where that hook is configured. It does **not** fence the directory. Things can land in an outbox from a parallel session with different settings, from you dragging a file in, from a `git merge` pulling in someone else's outbox, from a script you write in three months.

So the roboport genuinely cannot trust that the inserter ran. That's not paranoia — that's your no-worktrees, multiple-parallel-sessions constraint making its consequences felt.

## What each one can actually know

| | Inserter | Roboport |
|---|---|---|
| Vantage | Inside one noun | Sees all nouns |
| Checks | **Schema validity** — is this a well-formed item on its own terms? | **Referential validity** — does the declared route resolve? |
| Catches | Missing/malformed fields, wrong item type for this producer, bad self-attribution | Destination doesn't exist, destination won't accept this type, two items colliding on one filename, duplicate IDs across outboxes |

And the part that makes this non-optional: **the inserter must not check destinations.** It could `stat` the path, but the moment it does, the producer knows about routing — and that's the exact separation you liked. Destination-checking at the inserter would collapse the boundary that makes this design hold up.

It maps cleanly too: a filter inserter checks the item as it picks up; the logistics network checks whether anything actually requests it. Item-level filter, network-level demand. Same split.

## The thing that follows from it

The two failures cost different amounts:

- **Inserter rejects** → blocking, immediate, in the session where you made the mistake. Cheap.
- **Roboport rejects** → the item already exists, can't be retroactively refused. Goes to the failure lane, you find out later. Expensive.

So: **push every check as early as it can correctly live.** The roboport gets *only* the checks that genuinely require global knowledge. Anything checkable locally should never be allowed to become a failure-lane item.

## One trap

Don't write two schemas. If the inserter and roboport each carry their own copy of "what a science ore needs," they will drift, and you'll get items that pass one and fail the other — a jam with no legible cause. **One schema definition, two consumers.**
