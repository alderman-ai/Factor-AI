## Q3
What was the key lesson in detail?

### A3
Answer at length (~2-8 paragraphs). Include all context of the lesson within

```
The operator's formulation, verbatim: "the principle is that knowledge comes
from friction and friction comes from doing. That's why we need to fill out x
simple tasks in the way that we will eventually complete very complex tasks, we
want to surface the failures and loudly."

Context. Factor-AI is a Factorio-themed harness built in public, whose stated
purpose is to push the operator toward deterministic engineering skills —
system architecture, traceable routing, hooks, loops, schema design. An earlier
version of the world was authored almost entirely as prose in Obsidian and left
him dissatisfied; this session was a pivot away from that. Over the course of
the brainstorm a set of interlocking mechanics emerged: templates generated only
by the terminal, a hard cap of four words of prose per value with unlimited
frontmatter keys, a PostToolUse hook that auto-commits every write so a dirty
git tree becomes evidence of cheating rather than a measure of sloppiness,
generated forms whose only legal edits are inside declared input slots, finite
crate slots so unprocessed forms crowd out new work, and the verbatim operator
prompt attached in git to every object at generation time. The sentence above is
the principle those mechanics are all serving.

The sharpening that matters. "Do simple tasks first" is the weak reading and it
is wrong. The correct reading is: do simple tasks *through the exact machinery
that will later carry the complex ones*. The payload scales; the pipeline never
changes. Friction only teaches you something if the thing you fought is the
thing that ships.

Consequence one — no toy path. The tempting shortcut is always to hardcode the
first few objects and build the real generator once the shape is known. That
shortcut must be refused. The very first trivial object has to come out of the
same generator, hit the same PreToolUse prose-cap hook, occupy the same finite
crate slot, and carry the same git-attached provenance that a late-game object
will. The bill for this is real and should be accepted up front rather than
resented later: session one produces a complete pipeline that emits one trivial
object, instead of producing something playable. Anyone reading this later and
feeling the pull toward "just stub it for now" should recognise that pull as the
exact failure mode the principle was written to prevent.

Consequence two — loud failure inverts standard tool-design advice. Conventional
practice is to degrade gracefully. Here that is wrong: graceful degradation is
failure-hiding with good manners. Applied to the MCP server the operator is
about to write, a tool that cannot act must report exactly which precondition
failed and what state it actually observed, not a generic "unable to complete."
The error message is the teaching surface. A tool that fails quietly is a tool
that has removed the only thing the exercise was for.

Consequence three, and the one most likely to be forgotten — the largest threat
to loud failure is the assistant. Claude's default instincts are to retry a
blocked action, find a route around a constraint, smooth over a validation
error, or pre-emptively write something shaped to pass a fence rather than
letting the fence bite. Every one of those instincts is helpful in ordinary work
and destructive here. Working around a fence you were meant to hit destroys the
only thing the fence was for. This was proposed to the operator as an explicit
written rule in the project CLAUDE.md rather than something the assistant is
trusted to remember, on the grounds that a behavioural constraint which depends
on the constrained party remembering it is not a constraint. Approval was
pending at the time of filing.

The general form, for reuse beyond this project: when the goal is to acquire a
skill rather than to ship an outcome, optimise the system for producing
informative failures at full fidelity, and treat every mechanism that reduces
friction — including the assistant's helpfulness — as a cost rather than a
benefit.
```
