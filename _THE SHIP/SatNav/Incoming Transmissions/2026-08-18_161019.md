```
The setup: this repository, Factor-AI, is a set of sibling working directories
on one machine. `_THE SHIP` is the operator-facing one, where sessions are
started. `_THE VAST UNKNOWN` holds the world engine — a Python MCP server —
and is off-limits to Ship sessions by rule. The engine had just been registered
as a stdio MCP server in the repo-root `.mcp.json`, and this session was the
first attempt to reach it. The Ship's own CLAUDE.md instructs the assistant to
call the engine's `scan` tool on session start.

The failure: the engine's tools were absent from the session entirely, and
`/mcp` reported `Failed to reconnect to the-vast-unknown: CONNECTION_CLOSED`.

The mechanism, once traced: `.mcp.json` declared the server with relative paths
— `command: "_THE VAST UNKNOWN/.venv/Scripts/python.exe"` and
`args: ["_THE VAST UNKNOWN/server.py"]`. Those paths are correct relative to
the repository root, where the config file lives. But Claude Code does not
launch a stdio MCP server from the directory the config was found in. It
launches it from the session's current working directory. This session's cwd
was `_THE SHIP`, so the path resolved to
`_THE SHIP/_THE VAST UNKNOWN/.venv/Scripts/python.exe`, which does not exist.
The process could not spawn, died immediately, and Claude Code surfaced that
instant death as `CONNECTION_CLOSED` — a message that describes the symptom
(the stdio pipe closed) and says nothing about the cause (the executable was
never found).

The generalisable lesson is the asymmetry: **a config file's discovery location
and its execution context are two different directories, and relative paths in
that config bind to the second, not the first.** Repo-root config that is
shared across sibling working directories therefore cannot use relative paths
safely unless every session is guaranteed to launch from the same place. In a
repo whose stated architecture is "many subfolders will be Claude working
directories as well", that guarantee does not exist by default — it has to be
declared and enforced.

A second, narrower lesson: the obvious-looking fix does not work.
`${CLAUDE_PROJECT_DIR}` looks like exactly the right tool — a stable project
root that does not depend on cwd. The Claude Code documentation rules it out
for this use. That variable is injected into the *spawned server's* environment,
not into Claude Code's own environment. Expansion of `${VAR}` inside the
`command` or `args` of a project-scoped `.mcp.json` reads Claude Code's env, so
the variable is not found; the config still loads, Claude Code emits a
missing-variable warning, and it passes the literal unexpanded `${...}` text
through as a path. Adding the documented fallback `${CLAUDE_PROJECT_DIR:-.}`
makes it worse in a quieter way: it resolves to `.`, which is the cwd, which is
the original bug with extra steps. `CLAUDE_PROJECT_DIR` is genuinely useful
*inside* a server process (`os.environ["CLAUDE_PROJECT_DIR"]`) for resolving
data paths; it is useless for locating the interpreter that starts that process.
The distinction is: it can tell a running server where the project is, but it
cannot help Claude Code find the server in the first place.

The operator's fix was a design decision rather than a repair. Rather than make
the config cwd-independent — via an absolute path, or an environment variable
set per machine — the operator declared that **the Ship is always the assumed
cwd for reaching the engine**, and the paths were rewritten as
`../_THE VAST UNKNOWN/...`. This keeps the repo free of machine-specific
absolute paths and of invisible environment dependencies, and it converts a
launch habit into an enforced rule: a session started anywhere other than
`_THE SHIP` will now fail to reach the world. That failure is intended. It is a
fence, and the fence is legible in a checked-in file rather than living in
someone's memory.

The cost of that choice, stated plainly so it is not rediscovered painfully
later: the repo-root `.mcp.json` is now Ship-specific despite living at the
root, and any future sibling working directory that wants the engine will hit
this exact failure and see the exact same uninformative `CONNECTION_CLOSED`.
The mitigation is not a code change but a documentation one — the Ship's
CLAUDE.md still claims the engine "loads for sessions started anywhere in this
repo", which is now false and needs correcting.

Diagnostic technique worth keeping: an MCP stdio server can be tested outside
Claude Code entirely by piping a single JSON-RPC `initialize` request into it
and reading stdout. That separates "the server is broken" from "the server was
never started" in one command, and it was what proved the engine itself was
healthy — it returned a clean handshake identifying itself as
`THE VAST UNKNOWN` — before any config was touched.
```
