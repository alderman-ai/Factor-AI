### CLAUDE (claude-opus-5) · 2026-08-17 14:39:01 +0200

All three are used, but they come from different traditions and they are not interchangeable — which is exactly why homegrown taxonomies get muddy.

## The short version

**Kind** answers *what is it, essentially.* **Type** answers *what pattern does it instantiate, and what can you do with it.* **Category** answers *where does it sit in my scheme.*

Or, by directionality: **kinds are discovered, types are specified, categories are imposed.**

## Kind

The most metaphysically loaded. "Natural kind" is a technical term — a grouping that carves nature at its joints and supports induction: gold, water, electron. Kripke and Putnam built a whole theory of reference on them. The defining property is that **membership isn't up to you.** You can't decide something isn't gold.

In applied ontology — Guizzardi's UFO, the OntoClean methodology — Kind has an even sharper definition: a **rigid sortal that supplies an identity principle.** Rigid means an instance can't stop being of that kind without ceasing to exist. Sortal means it answers "what is it?" and tells you how to count and re-identify instances. In that framework every individual instantiates **exactly one** Kind, and everything else it is — role, phase, status — hangs off that.

## Type

The oldest useful contrast here is Peirce's **type/token**: "the word 'the' appears three times in this sentence" — three tokens, one type. Type is the abstract pattern, token is the concrete instance.

In computer science, type drifted toward **constraint and substitutability** — a type says what operations are permissible and where a value can stand in for another. Crucially, types are **multiple and non-rigid.** A thing inhabits many types at once, and can gain or lose them. In UFO, "type" is the umbrella term and Kind is one *sort* of type.

So: type is functional, kind is essential.

## Category

Aristotle's *Categories* were the ten highest genera — substance, quantity, quality, relation, and so on. Kant's were categories of the understanding. The through-line is that **a category is a top-level partition**, not a mid-level grouping.

Modern formal ontologies keep this: BFO's continuant/occurrent split is categorial. But in ordinary usage "category" has decayed into "any grouping I find convenient," which is why it's the weakest of the three unless you define it locally.

## The caveat

Usage genuinely isn't uniform. Analytic metaphysics, applied ontology (BFO/UFO/DOLCE), and CS type theory all use these words with different precision and occasional outright conflict. Nobody owns them.

## What this is worth to your taxonomy

Don't use all three as loose synonyms. That's the standard failure, and it produces a document that can't answer questions. Pick the distinctions you actually need and define them in the Lexicon.

The most useful tool you can steal is **OntoClean's rigidity test**, because it's mechanical:

> Can this thing stop being an X and still be the same thing?

If **no**, X is a kind. If **yes**, X is a role or a phase, and you're one level down.

Run that on your own components and it'll sort them fast. Is `Inserter` something a component *is*, permanently — or something a component *does* for a while, and could stop doing while remaining the same component? Because those two answers give you two completely different taxonomies, and the test tells you which one you're actually building before you've written it down wrong.

Two different answers depending on scope, and for your case they conflict on one point.

## The general YAML answer

**RFC 3339**, which is a strict profile of ISO 8601:

```yaml
created: 2026-08-17T14:32:00Z        # UTC
created: 2026-08-17T16:32:00+02:00   # with offset
created: 2026-08-17                   # date only
```

Unquoted, uppercase `T` and `Z`, and **always carry a timezone**.

The wrinkle is that YAML doesn't agree with itself. YAML 1.1 defined a `timestamp` type; **YAML 1.2 dropped it from the core schema** — which only has null, bool, int, float, string. So what you get back is parser-dependent:

| Parser | `created: 2026-08-17` becomes |
|---|---|
| PyYAML (YAML 1.1) | `datetime.date` object |
| js-yaml v4 | plain string |
| Go `yaml.v3` | `time.Time` only if the target field is one |

**The practical rule: quoting decides the type.** `created: 2026-08-17` may become a date object; `created: "2026-08-17"` is always a string, everywhere. If you want stability across tools, quote it and parse it yourself.

## The Obsidian answer

Obsidian uses **ISO 8601, extended syntax, second resolution, local time**:

```yaml
created: 2026-08-17          # Date
created: 2026-08-17T14:32:00 # Date & time
```

Unquoted. And per Obsidian's own docs, they **don't plan to let you choose a different format** — so this isn't a preference, it's a constraint.

## Which means, for your science files

Match Obsidian exactly. If you write `Z` or `+02:00`, Obsidian won't recognise it as a Date property — it degrades to text, and you lose date sorting and filtering in Bases and Dataview. Since the Lab is a knowledge base you'll be querying, that's the whole value gone.

**One gotcha worth deciding on now, not later:** Obsidian's format has **no timezone**. You're in Czechia, so that's a silent 1–2 hour ambiguity depending on DST, and it only bites when something outside Obsidian reads these files — a script, a publishing pipeline, anything correlating a science entry against a git commit timestamp.

If that matters, the clean pattern is two fields: `created` in Obsidian's format for the UI, and a separate quoted UTC string for machines. If it doesn't matter, ignore me and use local time. But that's a lexicon decision, so make it once and write it down rather than discovering the inconsistency in three weeks.

Path format won't cut your tool use — that lever isn't where you think it is.

## Why the premise doesn't hold

Both absolute and relative paths cost me **zero** extra calls. When I read a file I know where it lives, so resolving `../The Lab/Lexicon.md` is arithmetic, not a lookup.

The axis that actually costs calls is **resolvable vs. requires-search**:

| Field value | Cost |
|---|---|
| `C:\Users\alder\...\Lexicon.md` | 1 read |
| `The Lab/Lexicon.md` | 1 read |
| `../The Lab/Lexicon.md` | 1 read |
| `[[Lexicon]]` or `Lexicon.md` | **search, then read** |
| a stale or wrong path | **failed read, then search, then read** |

So bare names cost you. Absolute paths don't save you.

## And absolute paths actively hurt here

- **They're machine-specific.** Your repo is public. Anyone who clones it gets `C:\Users\alder\...` and a pile of dead links.
- **They break when you move the folder** — and you've already moved Lexicon and Taxonomy once today.
- **Obsidian won't follow them.** Obsidian resolves within the vault; a Windows filesystem path is just text to it. You'd lose backlinks and graph view — the entire point of a knowledge base.
- Minor, but they put your username in a public repo.

## What to actually use

**Vault-root-relative:** `The Lab/Lexicon.md`

One anchor, no ambiguity, portable across machines, resolvable by me without searching, and Obsidian follows it. It also beats `../`-style relative paths because it **survives file moves** — given how much you're still rearranging, that matters.

Set **Settings → Files & Links → New link format → "Absolute path in vault"** and Obsidian will generate that shape for you instead of shortest-path. Despite the name, that's vault-root-relative, not filesystem-absolute.

**One YAML gotcha:** if you want a real Obsidian link in a property, it must be quoted.

```yaml
mined_from: "[[The Lab/Lexicon]]"   # link + backlink
mined_from: [[The Lab/Lexicon]]     # parses as a nested array
```

Unquoted `[` starts a flow sequence in YAML. Silent, and it'll look fine until something queries it.

## Where the halving actually lives

**Denormalise the fields you query on.** A pointer costs me a read; a value costs me nothing. If `Mined by: M-001-Science Ore` is all I ever need, I never open M-001. If I have to open M-001 to learn what it *is*, then that fact belonged in this file too.

Duplication is the tradeoff — denormalised fields can drift from their source. But your artifacts are immutable, so a field copied at mint time is frozen against a frozen source. Drift can't happen. Your architecture already paid for this optimisation; you just haven't spent it yet.

Five blanks mined, zero smelted, and I stopped before spending any. Here's why, and the rest of the feedback.

## What's genuinely strong

**Your fence is physical, not instructed.** This is the best thing in the build. A prose rule saying "always use the template" is a rule I can forget, reason around, or lose to compaction. Five files that must exist on disk before an output can exist is a constraint made of inventory. You wanted to learn deterministic enforcement and you got there *without hooks* — scarcity did the work. When you said "if you run out I'll have to mine more," that sentence was literally true, and that's the whole achievement.

**The contract travels with the artifact.** Putting the fill instructions in the template body rather than in the skill means the instructions can't drift from the thing they govern. If you'd put them in `/science`, you'd have two files to keep in sync forever.

**You versioned the template itself.** `CL-Science Ore Patch/Science Ore Patch_v1.md` means when the template changes, old sciences stay interpretable against the template they were minted from. Most people discover they needed that after it's too late.

## The blocking problem: "smelting" is doing two jobs

You spotted this in conversation and asked me to help untangle it. **The ambiguity then shipped into the template anyway.**

`Ontology.md` says: *"Smelted files are filled in templates."* The template body agrees — fill it in, flip `Type` to `Smelted`, rename, move. So **filling = smelting**, one operation.

But you also described a second thing: *"a system of smelting five entries into a single good idea."* That's a different operation entirely — many filled ores in, one refined artifact out.

Both are currently called smelting. And your theme already gives you the right answer for free: in Factorio, ore → plate is **smelting**; plates → component is **assembling**. Five-into-one is not a smelter, it's an assembler. You have the vocabulary, you just haven't spent it.

**This also resolves the contradiction I flagged earlier.** You told me smelting emits a *new* artifact with lineage back to the source. The template does the opposite — it mutates the ore in place and moves it. Both designs are defensible, but they're different systems:

- **Move-in-place** — one document accumulates its whole lifecycle. Simple, no duplication, and `Mined on` / `Smelted on` in one file gives complete provenance. Cost: no re-smelting, and mutation-in-place gives back the clobber immunity you'd otherwise get free.
- **Emit-new** — the filled ore survives, the plate points back. Re-runnable, append-only, clobber-immune. Cost: two files per learning, and you need the reverse pointer discipline.

## Defects, in severity order

1. **`## Q1` appears twice** (lines 46 and 61). The second should be Q3. Your contract says "fill in the answers in the `A<N>` section" — with two A1s, that instruction is ambiguous, and this is the section that carries all the actual value.
2. **`"Smelting Session ID:":` has a trailing colon inside the quoted key.** The property is literally named `Smelting Session ID:`. Any Base or Dataview query against `Smelting Session ID` returns nothing, silently. This is the YAML-colon trap — you quoted to escape it and kept the colon inside.
3. **`Type` is being used as a phase field.** `Patch → Mined → Smelted` is a lifecycle, and by your own rigidity test those are phases, not types. The field name is now lying about what it holds. `Phase` would be honest.
4. **`S-Node` is used in all three Lab docs and defined nowhere.** Undefined vocabulary in the document that defines vocabulary.
5. **`Output Location` points at a folder that doesn't exist**, and it's nested *inside* the miner — output living inside the extraction machine.
6. **The Q2 fence contains the literal string `Null`**, which is the sentinel you decided against two hours ago.

## The knowledge-management gap

**You've built a capture system. You have not yet built a retrieval system.** That's the honest assessment, and it's the thing that will actually hurt.

Intake is excellent. But `Taxonomy.md` is empty, there's no index, and — the biggest one — **there is no subject field anywhere.** `Category: Science` describes what kind of *ore* it is, not what the science is *about*. Two sciences on completely unrelated topics are indistinguishable in frontmatter.

At 200 entries you will not be able to find anything. Everything of value lives in free-text inside a code fence, and nothing above it says what the entry is about. A knowledge base is judged on retrieval, not capture, and right now retrieval has nothing to grip.

Related: your rule that answers must be self-contained is genuinely good for durability — but combined with zero cross-linking it makes every science a silo. You want both. Self-contained *and* linked.

That's not fatigue talking, and it's not just "normal in Factorio" — though it is.
