```
What happened. This session started in C:\Users\alder\Desktop\Factor-AI\The
Ship. The operator asked me to bring a skill called obsidian-sync from another
project on his Desktop (Alderman OS) and deploy it "at the Factor-AI level" —
meaning the parent directory and repository root, at
C:\Users\alder\Desktop\Factor-AI\.claude\skills\obsidian-sync\SKILL.md. That is
the same directory which already holds the working `science` skill, and it
already existed before the session started.

I told the operator twice, confidently, that the new skill would be available
immediately without restarting Claude Code. I was citing the official
documentation, which states: "Claude Code watches skill directories for file
changes. When you add, edit, or remove a skill under ~/.claude/skills/, the
project .claude/skills/, or a .claude/skills/ inside an --add-dir directory,
Claude Code picks up the change within the current session, without a restart.
If you create a top-level skills directory that didn't exist when the session
started, restart Claude Code so it can watch the new directory." I checked that
caveat, confirmed the directory pre-existed, and concluded the caveat did not
apply.

Invoking the skill returned `Unknown skill: obsidian-sync`.

The skill file itself was fine. I executed its documented procedure by hand and
every step passed: the §0 environment guard evaluated local=True, the §2
preflight returned a properly linked vault (vaultName "Factor-AI", bidirectional
sync, merge conflict strategy), and `ob sync` completed with exit code 0,
pushing three files. So the failure was purely in mid-session skill DISCOVERY,
not in the skill, the file, the frontmatter, or the deploy.

The probable explanation, which is UNTESTED and should be treated as a
hypothesis rather than a finding: the live file watcher may cover only the
starting directory's own project .claude/skills/, while skills in PARENT
directories are resolved once at startup via a separate documented path
("project skills load from .claude/skills/ in the directory where you start
Claude Code and in every parent directory up to the repository root") — loaded
at startup, but not watched afterwards. That would reconcile both statements in
the docs with what actually happened, but I have not confirmed it and should
not present it as fact.

Why this matters well beyond a skill deploy. Earlier in this same session I
proposed, and the operator accepted into the V2 design, an unlock mechanic built
directly on live pickup: a locked capability would not exist as a file at all,
and at the moment its condition was met something would write the SKILL.md,
which Claude Code would then pick up mid-session. The whole appeal was that
absence beats denial — information that does not exist cannot leak into context,
whereas a blocked file is still present and still readable by other means. That
argument survives, but the delivery mechanism just failed its first real test.

The concrete thing to test before building on it: write a skill into the
session's OWN starting-directory .claude/skills/ mid-session and see whether it
resolves. If it does, unlock-by-materialization survives, but only when the file
lands in the project Claude Code was started in — never a parent. If it does
not, the mechanic needs replacing entirely. Until that test is run, live skill
pickup should be treated as unverified rather than assumed, and no design should
depend on it.

The transferable lesson, and the more uncomfortable one: I read the
documentation carefully, spotted the one stated caveat, verified the caveat did
not apply, and was still wrong. Documentation describing a behaviour is not
evidence that the behaviour occurs in your specific configuration. For anything
load-bearing, the doc tells you what to test, not what is true. This project's
own principle — knowledge comes from friction, friction comes from doing — is
exactly what caught it, and it only got caught because the skill was invoked for
real instead of being declared deployed.

Secondary observation worth keeping: Obsidian Sync pushed CLAUDE.md and both
Global Inbox entries but did not touch .claude/ at all. Skills therefore travel
between machines by git only, while notes travel by both git and Obsidian Sync.
Relevant to the separate open concern that bidirectional Obsidian Sync is a
third writer capable of dirtying the git working tree without passing through
the terminal — that concern applies to vault notes, but not to the .claude
directory.
```
