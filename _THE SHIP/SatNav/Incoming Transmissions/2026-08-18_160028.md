```
A CLAUDE.md instruction and a hook are not two flavors of the same thing.
They are different mechanisms with different failure modes, and knowing
which to reach for — and in what order — is a core harness-design skill.

Context: the operator wanted new Claude Code sessions started in the Ship
to automatically check whether the project's MCP server (the world engine
`the-vast-unknown`) is connected, and if so, call its `scan` tool and pick
up the run in progress. The operator asked "what do I put in CLAUDE.md to
get you to check if the server is live, and if so jump in?" The assistant
drafted the CLAUDE.md text — but flagged what that text actually is: a
prose instruction. CLAUDE.md content is read by the model and followed by
the model, which means compliance is probabilistic. The model can forget
it, deprioritize it under a crowded context, or follow it inconsistently
across sessions. Nothing detects the failure; the instruction just quietly
doesn't happen.

The deterministic alternative is a hook — in this case a SessionStart
hook, which the harness executes mechanically on every session start,
whether or not the model remembers anything. A hook cannot forget. Its
failure mode is loud (a script errors) rather than silent (a sentence
goes unread). This maps onto a general hierarchy this project keeps
rediscovering: prose that asks for behavior is the weakest fence,
validated structure is stronger, and harness-enforced mechanism is
strongest. The same session had already hit this pattern twice — a
schema gate beats a request to "keep fields consistent," and a
write-through state journal beats a save ritual someone must remember.

The actionable ordering, which is the real tip: ship the prose version
first, then graduate it to a hook once the behavior is understood. Not
because prose is good enough, but because hooks encode decisions, and
encoding a decision you haven't lived with yet is premature — this
project's own intake doctrine says templating ahead of the data is the
failure to avoid. The CLAUDE.md text costs one minute and is sufficient
to start playing Run 002; after a run or two reveals what "jump in"
should concretely do (what gets scanned, what gets reported, what
happens when the server is absent), that settled behavior becomes a
SessionStart hook and stops depending on the model's memory at all.

Secondary detail worth keeping: the session-start check itself is just a
tool call — the model calls `scan` and either gets an answer (server
live, report the sweep) or finds the tool missing (server not connected,
say so and stop). No file crawling, no process inspection. The MCP tool
surface is its own liveness probe.
```
