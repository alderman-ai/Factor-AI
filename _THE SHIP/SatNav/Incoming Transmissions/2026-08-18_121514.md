```
The lesson: a tool's storage model constrains the ontology you can express
in it, and you find the boundary by attempting the expression, not by
designing against it in advance.

Context. This project resets its world many times on purpose, and the
requirement was that those reset cycles be legible to someone browsing the
repository afterwards — that a reader could see a run's progress and then
see the file tree mostly deleted, with The Ship surviving as the durable
ledger. Git tags were chosen as the mechanism: immutable named coordinates,
pushed to GitHub, browsable as snapshots. The operator then designed the
naming scheme, in the project's own diegetic voice: BITER ATTACK!! for the
destruction that ends a run, SAME SHIP DIFFERENT DAY for the landing that
begins the next one, PROJECT_START as a one-time origin marker, and RUN_002
as a grouping concept meaning "the whole second run".

Git rejected this in three independent ways, each attempted and each
producing a real error rather than an anticipated one.

First, spaces. `git tag -a 'BITER ATTACK!!'` returns `fatal: 'BITER
ATTACK!!' is not a valid tag name` with exit code 128. The reason is that
refs are literally files on disk under `.git/refs/`, so ref names inherit
path constraints — space, tilde, caret, colon, question mark, asterisk,
bracket and backslash are all forbidden. Notably `!!` was legal the whole
time and survived into the final scheme unchanged. The instinct to assume
the exclamation marks were the problem would have been wrong, and testing
rather than assuming is what preserved them.

Second, uniqueness and the file/directory conflict. Tag names must be unique
per repository, so a bare `BITER_ATTACK!!` could only ever mark one reset —
`fatal: tag 'BITER_ATTACK!!' already exists` on the second attempt. That
alone forces a discriminator into every name. But the deeper failure came
when trying to use RUN_002 both as a standalone tag and as a namespace
prefix: `fatal: cannot lock ref 'refs/tags/RUN_002/BITER_ATTACK!!':
'refs/tags/RUN_002' exists; cannot create 'refs/tags/RUN_002/BITER_ATTACK!!'`.
Because a ref is a path, RUN_002 can be a file or a directory and never
both. The solo grouping tag and its children are mutually exclusive.

Third, and most fundamentally, a tag pins exactly one commit and cannot span
a range. "RUN_002 solo means the whole second run" was not expressible as a
tag under any naming scheme, because that is not what a tag is. This was the
useful failure. A run genuinely is a range, git has first-class range syntax
for it (A..B), and the correct model was therefore two pins per boundary
with the run being the span between them — not one tag trying to denote an
interval.

Two smaller findings came out of the same testing. Tags sort
lexicographically, so RUN_10 sorted before RUN_3 in a bare `git tag -l`
listing; zero-padding to three digits fixes this everywhere, including
GitHub's tag page, whereas the `--sort=version:refname` flag only works when
someone remembers to type it. And annotated tags record the date the tag was
created, not the date of the commit it points at — three test tags all read
2026-08-18 while pointing at commits from 2026-08-17. The field that tells
the truth about when a run actually ended is `%(*committerdate)`, where the
asterisk dereferences to the tagged commit.

That produced a rule worth generalising: put in a name only what the tool
cannot tell you. Git already stores both relevant dates, so a date in the
tag name is redundant; the run number exists nowhere except in the operator's
head and the Ship's ledger, so that is what the name has to carry.

The most valuable part was not any individual constraint but the direction of
influence. The file/directory conflict forced the namespace-prefix scheme
(RUN_002/BITER_ATTACK!! rather than a solo RUN_002), and that scheme then
resolved a completely separate open question that had been argued about
earlier in the session on its own terms: whether the number in a boundary tag
referred to the run that died or the run that was born. Under the prefix
scheme the ambiguity simply cannot arise, because the namespace carries the
ownership — RUN_002/BITER_ATTACK!! unambiguously means the death of run 2 and
RUN_003/SAME_SHIP_DIFFERENT_DAY unambiguously means the birth of run 3. A
mechanical constraint from the storage layer settled a semantic argument that
had no obvious resolution when treated as a naming preference.

The method note is the transferable part. Every one of these was surfaced by
running the command and reading the real error, not by reasoning about git's
rules beforehand. Reasoning in advance would have caught the spaces and
probably the uniqueness, but would very likely have missed the file/directory
conflict and would have had no reason to discover that the resolution of that
conflict also resolved the numbering ambiguity. Attempting the expression
generated design information that designing against the constraint would not
have produced.
```
